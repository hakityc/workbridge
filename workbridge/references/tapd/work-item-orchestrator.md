# Flow 工作项编排契约

Requirement 和 Task 共用一套编排管道，但不是一个操作。当前 Provider 是 TAPD；字段名和工具名由 Provider Adapter 映射，下面的字段是 Flow 的规范语义。

## 操作边界

支持四个可独立执行的操作：

| 操作 | 输入 | 产出 | 默认不做什么 |
|---|---|---|---|
| `requirement.create` | 目标、范围、验收点、优先级、规格来源 | Requirement 草案或远端需求 | 不创建 Task、不排期、不流转状态 |
| `requirement.update` | 需求 ID + 明确变更集 | 变更草案或更新后的 Requirement | 不覆盖未点名字段、不删除人工内容 |
| `task.create` | 父 Requirement、任务切片、owner、优先级、工作窗口 | Task 草案或远端任务 | 不自动写 effort；日期窗口未确认时只保留草案 |
| `task.update` / `task.schedule` | Task ID + 明确字段变更 | 更新草案或排期结果 | 不借排期修改 owner/status |

用户说“拆任务并排期”时才串联：

```text
intake → task plan → task.create/update → task.schedule → readback → report
```

用户只说“创建/修改需求”时停在 Requirement 操作；用户只说“补工时/排期”时停在 `task.schedule`。每一步都可以只产出草案，不要求后续步骤必须执行。

## 统一管道

Requirement、Task 的远端写入都按以下顺序执行：

1. **Resolve**：解析本轮工作项、Provider、workspace 和实体 ID；新输入优先于旧分支绑定。
2. **Read**：读取目标完整字段；创建 Task 前读取父 Story 和同 Story tasks，更新前读取旧值。
3. **Normalize**：把自然语言变成结构化变更集，区分用户明确值、继承值、AI 建议值和待询问值。
4. **Validate**：检查能力、权限、owner 范围、必填字段、日期顺序和字段映射。
5. **Dry-run**：展示对象、旧值 → 新值、来源（明确/继承/建议）、影响和待确认项。
6. **Confirm**：按 `safety-policy.md` 等待远端写入确认；本轮已明确“直接创建/写回”时，展示短 dry-run 后继续；团队范围任务仍要二次确认。
7. **Write**：只提交已确认的字段；不把空值当成覆盖指令。
8. **Readback**：重新读取目标并校验关键字段；失败时标记“写入未确认”。
9. **Report**：输出链接、实际写入字段、跳过项、缺失能力和下一步。

普通需求无需 Git 或 Manifest；只有正式规格发布与按规格开发才执行规格准入。本管道不取代适用场景中的 `spec-authority.md`、`team-policy.md` 或 Provider 能力门禁；它只规定它们如何组合。

## 字段规则

### Requirement

创建的 write-ready 草案至少要有：

- `title`：稳定、可搜索，不把 Task 清单塞进标题。
- `description`：目标、in-scope、out-of-scope、must/should 和可执行验收点；Flow 管理的需求必须使用受管区块。
- `priority`：优先级必须有值。优先采用用户明确值；否则根据业务影响给出带“AI 建议”标记的 P0/P1/P2/P3，无法判断时询问。
- `source`：若来自产品规格，保留 `spec_id` 和精确 commit；仅来自产品规格的正式发布在缺少 Manifest 时标记为规格草案；普通需求创建/修改不要求 Manifest。

`owner`、`iteration`、`module` 等字段只有用户或团队策略要求时才加入；字段未点名时不臆造。`status` 默认保持 Provider 初始值，不因创建或修改需求自动流转。

修改需求必须先形成字段级变更集：

- 只改用户点名的字段，未点名字段保持旧值。
- Flow 管理的 Story 只更新规格受管区块；区块外人工内容保留，正式内容回到产品 Repo 后再发布。
- 非受管 Story 的 description 更新要展示完整旧文 → 新文差异，不能静默整段覆盖。
- 需求更新完成后不隐式创建 Task；需要拆任务时进入独立的 `task.create`。

### Task

任务可写回前必须具备：

| 字段 | 规则 |
|---|---|
| `story_id` | 必须是已读取并确认的父 Story，不得把 Task ID 当父需求 ID |
| `name` | 使用 profile 前缀 + 动词 + 对象 + 可验收范围，避免“开发一下” |
| `description` | 目标、边界、对应 `AC-*`、输入/输出、验证方式和依赖 |
| `owner` | 默认当前 `user_nick`；明确指定他人时仍受 profile 和权限限制 |
| `priority` | 优先继承父需求优先级；父需求为空时给出 AI 建议并在 dry-run 标注，歧义时询问；不得留空写回 |
| `effort` | 由 `effort-scheduler.md` 分段估算并换算为 Provider 需要的单位；排期写回时不得用空值表示“待估”；用户明确“只拆任务不写工时”时可只保留建议值 |
| `begin` / `due` | 远端创建/排期必须是工作日且 `begin <= due`；创建任务时未知就主动询问，不能带空日期写回 |

`iteration`、`module`、依赖和关联 AC 是增强字段；Provider 不支持时列出 gap，不伪造写入。`status` 不属于默认创建/排期字段，除非用户明确要求状态流转并通过对应 Gate。

## 任务拆分

先用 Story 的 must/should、原型、已有 tasks 和代码落点计算“独立交付切片”，再决定数量。拆分依据按优先级为：独立验收点、前后端/质量边界、依赖链、风险隔离；不是按文件数量机械切分。

| 复杂度 | 常见范围 | 拆分建议 |
|---|---:|---|
| 简单 | 1~2 条验收点、单角色、无新接口 | 1 个任务；有独立质量交付时为 2 个 |
| 中等 | 跨页面或有一条接口/权限链 | 2~3 个任务，按可独立验收的层或链路拆 |
| 复杂 | 多角色、多接口、多模块或明显联调风险 | 3~5 个任务，至少覆盖实现、联调/质量等必要切片 |
| 超出范围 | 需要超过 5 个平行任务 | 先按里程碑/子范围归并并询问，避免生成任务垃圾 |

规则：已有任务已覆盖的切片不重复创建；每条新任务必须能单独验收；“分析一下”“跟进一下”只有明确交付物时才能成为 Task。没有足够信息时输出拆分草案并列出缺口，不用占位任务填数。

## 日期询问 Gate

创建 Task 或写回排期时，只要 `begin` 或 `due` 缺失，就暂停远端写入并主动问：

> 这些任务的工作窗口是什么？请给开始日期和结束日期；如果每条任务不同，请按任务列出。确认后我再生成排期 dry-run。

可以先展示不含日期的拆分草案，但必须明确“等待日期，尚不可写回”。不能用今天、Story 截止日或 AI 推测日期静默补齐；只有用户明确授权继承某个日期窗口时才可继承，并在 dry-run 标注来源。明确“只拆任务不写工时”只豁免 effort，不豁免日期询问。

更新已有 Task 时，修改 effort 不自动重算日期；修改日期不自动改 effort。两者都要变更时分别展示旧值 → 新值。
